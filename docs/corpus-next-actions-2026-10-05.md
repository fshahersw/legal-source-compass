## PDF storage and safe deduplication

The live read-only `corpus_admin_pdf_dedup_index_v1` returned **153,994 registered content-addressed PDF objects (95,040,922,530 bytes)** and **107,742 CourtListener-family asset associations**: 86,258 public-locator associations and 21,484 native CourtListener associations. All listed native IDs had one hash version; no ambiguous SHA-1 object identities were reported. The RPC is deliberately limited to CourtListener and public-locator assets; it does not prove DocketBird coverage and cannot detect unregistered bucket objects. These figures describe the registry, not duplicate bytes across the entire bucket.

The existing `scripts/ingest/pdf-dedup.mjs` and `scripts/ingest/report-pdf-queue-dedup.mjs` safely avoid a second download when a previously read-back-verified object matches provider SHA-1 or an exact stable URL. `scripts/ingest/backfill-pdfs-to-supabase.mjs` stores objects under a SHA-256-derived key with upsert disabled, then verifies a complete authenticated cloud readback before registration. `database/contracts/corpus-pdf-assets-v1.sql` makes SHA-256 the primary key of `pdf_objects`; the dedup-index RPC is read-only. These parts prevent duplicate registration through this path, but do not remove existing storage objects.

The existing `scripts/admin/cleanup-exact-local-metadata.ps1` is a separate, pinned cleanup of 88 byte-identical local metadata copies. Its completion is documented in `docs/seeger-weiss-pdf-library-progress-2026-10-02.md`; it is not a PDF object cleanup mechanism. I found no PDF bucket deletion/garbage-collection contract or script. Before any PDF removal, add a read-only plan that inventories all object keys in `corpus-originals`, joins them to `corpus_ingest.pdf_objects` and every asset/observation reference, verifies candidate bytes and a retained canonical object by full hash readback, and records a reversible before-image/receipt. A key absent from one PDF index is not enough evidence for deletion.

The reusable SELECT-only inventory is now in [corpus-storage-audit.sql](../scripts/admin/corpus-storage-audit.sql). It compares bucket objects with PDF objects, downloadable artifacts, PDF capture/metadata keys, all 324 exact entries from the private bundle manifest, legal-archive manifest keys and legal image `object_key` fields. The SQL reports known-reference misses/size conflicts, hash-looking duplicate-key candidates (including the legacy `corpus-originals/<2 hex>/<64 hex>` form), PDF association occurrences versus unique hashes, relation/index/dead-tuple statistics, top dataset counts, and sampled text/item/detail widths.
